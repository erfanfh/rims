# سامانه خودارزیابی بلوغ مدیریت ریسک RIMS 2022 — راهنمای اجرا

این مخزن یک **پروژه Full-Stack** شامل رابط فارسی راست‌به‌چپ، پرسش‌نامه ۴۲موردی اصلی، ورود با ایمیل و کد دعوت، ذخیره پاسخ‌ها در PostgreSQL، الگوریتم امتیازدهی در تراکنش سرور، گزارش با نمودار راداری، پنل مدیریت و تولید Excel با ۹ کاربرگ است. **این بسته به‌خودی‌خود سایت منتشرشده نیست** و برای تبدیل به خدمت عملیاتی باید با حساب واقعی Supabase و میزبانی وب پیکربندی و آزمایش شود.

## ۱. مبنای علمی و تصمیم‌های باز

- منبع اول: فایل پایان‌نامه «پایان نامه (Repaired).docx»، بخش RIMS 2022، صفحات چاپی ۲۳ تا ۲۷ فصل دوم.
- منبع دوم: فایل `RIMS-questionnaire(1).html`؛ داده‌های JSON آن **بدون تغییر متن** به `src/data/questionnaire.json` منتقل شده‌اند؛ هش SHA-256 HTML اصلی: `e4f2a4bb2e5313dce76937738f7a2b77facc20ac0a1827dc78730c28e894513e`.
- پرسش‌نامه: ۳۷ سؤال شماره‌دار + ۵ سؤال سطح هدف = ۴۲ مورد. از ۳۷ سؤال، فقط q3 تا q37 (۳۵ شاخص) برای امتیاز بلوغ به کار می‌روند؛ q1 و q2 داده‌های زمینه‌ای‌اند. پنج پرسش سطح هدف نیز مستقل ذخیره می‌شوند.
- وزن ارکان: هم‌راستایی با راهبرد ۰٫۲۵؛ فرهنگ و پاسخ‌گویی ۰٫۳۰؛ قابلیت‌ها ۰٫۲۰؛ حاکمیت ۰٫۱۳؛ تحلیل‌گری ۰٫۱۲.
- برای هر رکن: میانگین حسابی نمره شاخص‌های آن رکن (۱ تا ۵). جمع موزون میانگین‌ها، امتیاز کل بین ۱ و ۵ را می‌دهد.
- **مرزهای رسمی Tier 1 تا Tier 5 از اسناد در دسترس با قطعیت قابل تأیید نیست**. هیچ آستانه پیش‌فرض در سیستم تعبیه نشده. فقط مدیر پژوهش می‌تواند با ثبت منبع، ماهیت ادعا و تأیید خود، دامنه‌ها را فعال کند. خروجی `tier` قبل از این تأیید خالی خواهد بود.
- چگونگی تجمیع نمرات چند نفر از یک سازمان یک **تصمیم روش‌شناختی پژوهش** است و در این نسخه انجام نمی‌شود. هر پاسخ‌دهنده مستقل گزارش می‌شود. شاخص شکاف هدف منهای وضعیت فعلی، یک شاخص تکمیلی پژوهشگر است.
- اعتبارسنجی محتوایی ترجمه، اخلاق پژوهش، تناسب ابزار با صنعت ساخت و پروتکل اجماع ارزیابان باید با استاد راهنما تصویب شوند؛ پیاده‌سازی فنی جایگزین تأیید علمی نیست.

## ۲. پیش‌نیازها

۱. رایانه دارای Node.js نسخه ۲۰ یا جدیدتر و npm.
۲. حساب Supabase و یک پروژه PostgreSQL ایجادشده.
۳. حساب میزبانی برای Next.js، مثلاً Vercel.
۴. آدرس ایمیل پژوهشگر و امکان دریافت ایمیل ورود یک‌بارمصرف.

## ۳. راه‌اندازی محلی

۱. محتویات zip را استخراج کنید و یک ترمینال داخل پوشه پروژه باز کنید.
۲. فرمان `npm install` را اجرا کنید.
۳. فایل `.env.example` را به `.env.local` کپی کرده و ۴ مقدار را وارد کنید:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://...supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=...
SUPABASE_SERVICE_ROLE_KEY=...  # محرمانه؛ فقط سرور
ADMIN_EMAIL=your.email@example.com
```

۴. در داشبورد Supabase، بخش **SQL Editor** را باز کنید و محتوای `supabase/schema.sql` را **یک بار** اجرا کنید. جدول‌ها، توابع امتیازدهی اتمی، قفل پاسخ نهایی و RLS فعال می‌شوند.
۵. فرمان `npm run seed` را اجرا کنید. خروجی موفق باید ۵ رکن، ۴۲ سؤال و ۲۱۰ گزینه را گزارش دهد. برنامه در صورت وجود ارزیابی ثبت‌شده، بازنویسی کاتالوگ را متوقف می‌کند تا متن پاسخ‌های تاریخی عوض نشود.
۶. در **Authentication → Providers → Email**، ورود با پیوند ایمیلی را فعال کنید. در تنظیمات **URL Configuration**، نشانی محلی `http://localhost:3000/login` و بعداً دامنه نهایی را در Redirect URLs مجاز قرار دهید. برای کاربران واقعی، محدودیت ارسال ایمیل پیش‌فرض Supabase را بررسی و در صورت نیاز SMTP مجاز تنظیم کنید.
۷. `npm run dev` را اجرا و `http://localhost:3000` را باز کنید.
۸. با ایمیل پژوهشگر وارد شوید و لینک را تأیید کنید. اگر حساب هنوز نقش مدیر ندارد، موقتاً صفحه تکمیل مشخصات می‌بینید.
۹. `npm run grant-admin` را در ترمینال اجرا کنید. اسکریپت فقط ایمیل تعیین‌شده در `.env.local` را با سرویس‌کلید سرور به مدیر ارتقا می‌دهد؛ هیچ کاربر عادی از طریق ثبت‌نام نمی‌تواند مدیر شود.
۱۰. مرورگر را تازه‌سازی کنید و به `/admin` بروید.

**هشدار امنیتی:** service role key را هرگز در GitHub، JavaScript مرورگر، فایل ارسالی یا `NEXT_PUBLIC_...` قرار ندهید. این کلید RLS را دور می‌زند. در صورت افشا، فوراً کلید را عوض کنید.

## ۴. گردآوری پاسخ‌ها

۱. مدیر در پنل «سازمان‌ها» یک شرکت را ثبت می‌کند.
۲. برای هر فرد در پنل «کدهای دعوت»، یک کد جداگانه (تصادفی و یک‌بارمصرف) تولید می‌کند. فقط هش SHA-256 کد در سرور ذخیره می‌شود.
۳. پاسخ‌دهنده با ایمیل وارد می‌شود، کد دعوت را وارد می‌کند، سازمان مربوط را مشاهده کرده و اطلاعات و رضایت آگاهانه خود را ثبت می‌کند.
۴. سامانه یک «ارزیابی جدید» با شناسه UUID می‌سازد. هر پاسخ با یک درخواست امن در پایگاه داده ذخیره می‌شود؛ تا پیش از ارسال موفق دکمه حرکت غیرفعال است.
۵. پس از تکمیل تمام ۴۲ مورد، «ثبت نهایی» فعال می‌شود. در **یک تراکنش پایگاه داده** امتیازهای پنج رکن و امتیاز کل محاسبه و پاسخ‌ها قفل می‌شوند.
۶. پس از ثبت نهایی، ارزیابی تازه در دوره بعدی مستقل ثبت می‌شود. پاسخ‌دهنده فقط به ارزیابی‌های خود دسترسی دارد.
۷. پژوهشگر در پنل، پرونده‌های کامل/ناقص را مشاهده و از اطلاعات Excel دریافت می‌کند.

## ۵. خروجی‌های پژوهشی

دکمه «دریافت داده‌های پژوهش در قالب Excel» به‌صورت پیش‌فرض هویت شخصی و نام شرکت‌ها را **حذف/با کد جایگزین** می‌کند و ۹ کاربرگ ایجاد می‌کند:
`Organizations`, `Respondents`, `Assessments`, `Raw_Answers`, `Question_Scores`, `Dimension_Scores`, `Maturity_Results`, `SPSS_Data`, `Data_Dictionary`.

- `Raw_Answers` هر پاسخ را همراه **نسخه متن سؤال و متن گزینه در لحظه پاسخ‌گویی** حفظ می‌کند.
- `Question_Scores` q1/q2 و سؤالات هدف را با پرچم «غیر شاخص رسمی» مشخص می‌کند.
- `SPSS_Data` یک سطر برای **هر ارزیابی** دارد؛ بنابراین اگر یک فرد در چند دوره شرکت کند، شناسه فرد در چند سطر تکرار می‌شود. این برای تحلیل‌های طولی صحیح‌تر است.
- امتیازهای ناقص به‌جای صفر، خالی می‌مانند.
- برای فایل شامل نام اشخاص، مدیر باید گزینه مخصوص آن را آگاهانه فعال کند و علت نیاز و مجوز اخلاقی داشته باشد.
- داده‌های بسیار عظیم (>۱۲۰هزار سطر در یک جدول) به صادرات صفحه‌بندی/جریان‌دار نیاز دارند. این نسخه برای حجم متعارف پایان‌نامه طراحی شده است.

## ۶. تست و اعتبارسنجی

```bash
npm run test
npm run typecheck
npm run build
npm run smoke  # پس از اجرای SQL و seed روی Supabase واقعی
```

تست‌ها مجموع وزن‌ها، ۳۵ شاخص، سطوح ۱ و ۵، عدم تعیین Tier بدون قانون و عدد هدف ۳٫۱۳۵ را کنترل می‌کنند. علاوه بر تست‌های کد، پیش از دعوت شرکت‌ها حتماً این سناریوها را **روی Supabase واقعی** با دو حساب مستقل بررسی کنید:

۱. حساب A نتواند پاسخ حساب B یا شرکت B را از URL/API مشاهده یا تغییر دهد.
۲. پاسخ ناتمام بعد از خروج و ورود مجدد بازگردد.
۳. کد دعوت مصرف‌شده قابل استفاده مجدد نباشد.
۴. درخواست تغییر پاسخ پس از submit رد شود.
۵. بارگذاری ۴۲ پاسخ باعث ثبت یک نتیجه نهایی واحد شود؛ درخواست submit مجدد رد شود.
۶. خروجی Excel از نظر تطبیق ۲۱۰ متن گزینه، شناسه‌ها، امتیازها و داده‌های گمشده با پایگاه داده تطبیق داده شود.
۷. از نمونه واقعی بدون اطلاعات هویتی، امتیاز پنج رکن مستقل در Excel بازتولید گردد.
۸. تأیید آستانه‌ها فقط توسط مدیر انجام شود و متن مستند مرزها در گزارش روش پژوهش ثبت شود.
۹. ثبت‌نام و نمایش نمودار روی تلفن همراه و مرورگرهای مختلف آزمایش شود.

**وضعیت اعتبارسنجی در زمان تحویل این بسته:** یکپارچگی کاتالوگ و قواعد فرمول با بررسی مستقل روی فایل‌ها کنترل شده‌اند؛ اجرای end-to-end و build با سرویس ابری در این محیط **انجام نشده‌اند**، زیرا دسترسی به حساب‌های واقعی Supabase/Vercel و دریافت وابستگی‌های npm وجود ندارد. نباید از این بسته بدون انجام مراحل فوق برای داده‌های حساس واقعی استفاده کرد.

## ۷. استقرار روی Vercel

۱. پوشه را در مخزن Git خصوصی قرار دهید. `.env.local` باید به دلیل `.gitignore` وارد مخزن نشود.
۲. در Vercel یک Next.js Project از مخزن بسازید.
۳. متغیرهای `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` و `SUPABASE_SERVICE_ROLE_KEY` را در **Environment Variables** پروژه قرار دهید. `ADMIN_EMAIL` فقط برای اسکریپت مدیریت محلی لازم است.
۴. در Supabase `Site URL` و `Redirect URLs` را به آدرس نهایی HTTPS به‌روزرسانی کنید.
۵. Build/Deploy کنید. دسترسی `/admin` باید نیازمند توکن و نقش مدیر باشد. کد سایت به‌تنهایی امکان ساخت حساب Supabase یا انتشار روی Vercel بدون مجوز شما را ندارد.
۶. از سامانه عملیاتی نسخه پشتیبان منظم، پایش خطا و سیاست نگهداری داده تهیه کنید و متن رضایت‌نامه را مطابق مصوبه اخلاق پژوهش تکمیل کنید.

## ۸. تصمیم‌ها/محدودیت‌های باقی‌مانده پیش از استفاده واقعی

- مرزهای Tier به امضای مسئول علمی پژوهش نیاز دارند؛ در UI هیچ مقدار پیش‌فرض معتبر وجود ندارد.
- نحوه ترکیب ارزیابی چند مدیر در یک سازمان هنوز تصویب نشده و خودکار انجام نمی‌شود.
- مدت نگهداری اطلاعات، راه ارتباطی مسئول حفاظت داده، رویه دقیق حذف/اصلاح داده پس از درخواست مشارکت‌کننده و قوانین محل میزبانی باید در پروتکل اخلاق/حریم خصوصی مصوب مشخص شوند. این نسخه امکان **خروجی ناشناس** دارد اما هنوز یک گردش‌کار خودکار حذف اطلاعات از Supabase Auth ندارد؛ برای پاسخگویی رسمی به درخواست حذف، فرایند اداری معتبر و توسعه تکمیلی لازم است.
- ورود Supabase Auth به طور پیش‌فرض از ذخیره نشست در مرورگر استفاده می‌کند؛ قبل از جمع‌آوری داده حساس، CSP و سیاست‌های مدیریت نشست باید در بررسی امنیتی استقرار نهایی بازبینی شوند.
- نمودارها و امتیازها جایگزین ممیزی اسناد سازمانی نیستند؛ برای کاهش سوگیری خوداظهاری، برنامه اعتبارسنجی میدانی تدوین شود.

## ۹. نگاشت ساختار فایل‌ها

- `src/data/questionnaire.json`: متن کامل پرسش‌نامه (بدون ویرایش)
- `src/lib/scoring.ts`: فرمول مستقل و تست‌پذیر بلوغ
- `supabase/schema.sql`: جدول‌ها، محافظت پاسخ‌ها، محاسبه تراکنشی و اعمال قواعد سطح
- `src/app/api`: APIهای امن ثبت پاسخ، ثبت‌نام، خروجی و پنل مدیر
- `src/app/assessment`: تکمیل پرسش‌نامه؛ `src/app/results/[id]`: گزارش راداری و چاپ PDF
- `src/app/admin`: مدیریت سازمان‌ها، دعوت، داده‌ها، Excel و قوانین Tier
- `scripts/seed.mjs`: انتقال داده‌های اصلی به DB؛ `scripts/grant-admin.mjs`: اعطای نقش مدیر پس از احراز هویت

## ۱۰. حدود استفاده و انتساب

RIMS و مدل آن متعلق به صاحبان حقوق مربوطه‌اند. انتشار یا استفاده عمومی از متن کامل پرسش‌نامه باید با حقوق نشر و شرایط مجوز متن اصلی سازگار باشد. این پروژه تأیید یا وابستگی رسمی به RIMS را ادعا نمی‌کند.
